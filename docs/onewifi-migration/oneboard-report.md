# OneBoard WebUI checkpoint (2026-10-13)

## Source changes

- `webui/src/App.jsx`: translated OneBoard dock/nameplate/navigation structure around the existing React views. The name comes from MDD auth status/login, host from the browser origin, and the connection badge from actual WebUI API-load state. Existing overview, devices, calls, messages, contacts, eSIM, keepalive, egress, notifications, settings and diagnostics destinations remain accessible. MDD cookie/CSRF calls, WebSocket and `GlobalSoftphone` were not replaced.
- `webui/src/oneboard.css`, imported by `webui/src/main.jsx`: OneBoard-derived 28px shell gutter, 196px floating glass dock, light/dark/auto palette, icon navigation rail, responsive nameplate and mobile glass bottom tabs. On short desktop windows the navigation rail alone scrolls, retaining theme and sign-out. On mobile, the closed drawer is visually and keyboard-hidden. Device-card corners/shadows and spacing are adapted to the MDD views.
- `webui/public/ONWIFI-LICENSE.txt`: retained source MIT notice for visual adaptations. No NEWONE JavaScript/API or Vue dependency was copied.
- `webui/tests/visual-preview.mjs`: project-local test-only built-app server with synthetic `VISUAL FIXTURE` auth and **zero** devices. This does not ship in the build, grant production access, or prove runtime integration.
- `webui/src/api.js`: native cookie/CSRF WeCom, Bark and SMS APNs test calls; the APNs request fixes `kind` to `sms` and exposes no VoIP synthetic test.
- `webui/src/views/NotificationProviders.jsx`, `webui/src/views/UnifiedPages.jsx`: WeCom/Bark destination, template, event and option forms plus separate SMS/VoIP APNs credentials on the existing Notifications page. All changes save through native `GET|PUT /api/settings`; the test controls send real requests and were not clicked in QA. A successful provider response is described as acceptance, never device delivery.
- `webui/src/notificationDestinations.js`, `webui/tests/notification-destinations.test.mjs`: unchanged masked URL arrays round-trip, while replacement requires the complete explicit list; mixed masks, empty enabled destination lists and more than ten URLs are rejected before submission. The server remains authoritative for HTTPS/provider validation and mask conflicts. APNs key paths stay server-side and unchanged masks survive save.
- `webui/src/i18n.jsx`: Chinese translations for the shell's five missing navigation labels and the new provider controls. `webui/src/oneboard.css` adds the destination editor's responsive wrapping.
- The visual fixture now includes synthetic masked provider fields. These are illustrative GET data; its generic PUT response does not emulate the native settings round-trip.

## Remaining gaps

- Actual authenticated MDD control-plane preview, reader/IMS/call/SMS/eSIM network-request traces, mobile clients and hardware were not available in this frontend checkpoint. A screenshot of the fixture cannot establish any of these.
- WeCom/Bark/APNs form source, native route wiring and synthetic desktop/mobile UI checks are present, but actual authenticated native PUT round-trip, APNs provider acceptance/device delivery and live hardware are unproven. The test-only fixture cannot validate server save or masked URL restoration. VoIP push has no synthetic test and needs a real call.
- No standalone carrier-profile CRUD editor was requested or added. Operational carrier matching and overrides belong to the backend; this report does not claim a verified WebUI projection.
- The original source has additional bespoke card variants; this checkpoint translates the shell, theme and basic device-card surface rather than pixel-identical every nested view. Compare against a live authenticated MDD session after integration.
- Earlier local preview servers on ports 5179 (normal login) and 5180 (synthetic fixture) were development-only; port 5180 was unavailable at final verification. Nothing was deployed to NEWONE or installed into the MDD production serving path.
