## Transport and ownership

- **FACT (B):** Both login flows use `POST /api/auth/login`, restore `GET /api/auth/session`, logout `POST /api/auth/logout` through `HttpTransport`; successful JSON must contain `data`, errors must contain structured `error`, bearer token is stored per origin and 401 expires the current session (`I/lib/features/auth/data/auth_api.dart:8-39`, `I/lib/features/auth/data/auth_repository.dart:24-62`, `I/lib/core/http/http_transport.dart:89-205`, A analogous). Default origin remains `http://192.168.1.88:6699` (`I/lib/core/config/base_url_policy.dart:2`, A same); it is a default, not runtime evidence.
- **FACT (B):** Normal Dart REST requests use the same origin-scoped token; call media WS uses an `access_token` query (`I/lib/features/calls/data/calls_api.dart:87-111`, A analogous), while native call gateway uses bearer header and origin-scoped leaf pin (`I/ios/Runner/Calls/CallGatewayClient.swift:76-125,178-210`; `A/android/app/src/main/kotlin/com/oneims/onewifi/calls/CallGateway.kt:14-43`). Native session gets token/origin/expiry/fingerprint from Flutter after sign-in; sign-out clears it (`I/lib/features/calls/state/call_session_binding.dart:50-109,168-195`; `A/lib/features/calls/state/call_session_binding.dart:42-143`). MDD helper has a separate in-memory token/CSRF and unconditional bad-certificate approval, and is not in this graph.
- **FACT (B):** Both native call engines consume `GET /api/calls/events` SSE snapshots, act on `POST /api/devices/{id}/calls/{dial,answer,hangup,dtmf}`, fetch metadata and upgrade WS on `/api/devices/{id}/calls/media?id={callId}` (`I/ios/Runner/Calls/CallGatewayClient.swift:51-57,94-123`; `A/android/app/src/main/kotlin/com/oneims/onewifi/calls/CallEventMonitor.kt:59-89`, `CallHttpActions.kt:16-39`).
