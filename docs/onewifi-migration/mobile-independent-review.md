## Blocking findings

1. **P1, iOS owner: cancelled outgoing dial can start after CallKit has ended it.** `IOS/ios/Runner/Calls/CallKitCoordinator.swift:949-953` sends `cancel` when the OS UUID has no dialog. `IOS/lib/features/calls/data/mdd_sip_background.dart:142-153,187-190` clears only `_pendingDial` and the registry; an already-running `_refreshLineMedia` resumes after cancellation and checks only session generation (`:145-147`), which is unchanged. It then calls `_sip.dial`, and `sip_call_service.dart:307-329` does not own a cancellation lease through `helper.call`. Trigger: user ends an outgoing call during a delayed provisioning response or asynchronous WebRTC start. Impact: SIP INVITE can originate after the native UI/CallKit call is gone, creating an orphan call. Add operation-UUID cancellation/tombstone checks before initiation and after asynchronous initiation, hang up any late dialog, and exercise deferred media and helper completion in a regression. Source command tests do not cover this native-to-Dart race.
2. **P1, iOS owner: SIP command errors are discarded while CallKit reports success.** `IOS/ios/Runner/AppDelegate.swift:33-40,58-61` invokes/flushes MethodChannel commands without inspecting completion/error. `CallKitCoordinator.swift:934-961` finishes start/answer/mute actions successfully after dispatch; outgoing has no timeout (`armBinding` at `:823-833` is only for incoming push). `mdd_sip_background.dart:129-153,294-323` can throw on revoked credentials, failed provisioning, unavailable SIP registration or media refresh. Trigger: a dial or answer with an offline/expired line, or Flutter engine command failure. Impact: persistent dialing/ringing CallKit state or an apparently answered call without SIP/media, with no actionable error or bounded cleanup. Correlate command result and OS UUID/generation, fail action/terminate with bounded timeout, and test an explicit Dart rejection and no callback.
3. **P1, Android call owner: native timeout does not cancel the Dart initiation.** `android/app/src/main/kotlin/com/oneims/onewifi/calls/AndroidSipBridge.kt:77-97` times out a MethodChannel invocation after 12 seconds. `CallCoordinator.kt:173-200` then fails local dial while `created` is null and cannot hang up a dialog. `android/lib/features/calls/data/android_sip_entrypoint.dart:109-143,266-302` may still be awaiting media/`sip_ua` initiation; its generation only changes on configure/clear, not native timeout. Trigger: slow provisioning/WebRTC exceeds native timeout but later completes. Impact: outgoing SIP call appears after the UI/Telecom command failed; later event has no owning Telecom session. Propagate an operation-owned cancellation/timeout to Dart and stop/hangup any late initiation. Existing `SipDialLeases` test checks map ownership only, not the real MethodChannel/timeout path.
4. **P1 product scope, Android/backend owners: late-registration pickup is not reachable.** `SipCallService.pickup` and `MddPickupReceipt.parse` exist, but Android production `AndroidCallHost.kt:14-25` wires a resident `SipCallEventSource`; `AndroidSipBridge.kt` and `android_sip_entrypoint.dart` have no push/OS UUID reservation/pickup command path. The original Android transport had no FCM process-wake provider. After process death or registration late in a ringing fork, Android cannot execute the required receipt-verified pickup or receive a cold wake. This is a missing acceptance path, not a claim that a nonexistent FCM provider regressed. Define an actual delivery/wake/identity contract or explicitly narrow acceptance to resident-service calls; test the end-to-end path rather than only shared registry primitives.
