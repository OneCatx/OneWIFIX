## Ownership and current call chains

1. **SIM to line:** reader monitor takes `hub.reader_lock`, reads identity, matches ICCID, refreshes reader binding, or calls `_ensure_card_draft` (`main.py:378-419,809-866`). A stopped draft is promoted only after missing identity/PIN/IMEI checks; promotion merges carrier defaults and pins modem's PIN/SWu/AMI slots (`main.py:1070-1144`). `_auto_start_hotplugged_line` consults device desired state and calls `_start_engine_checked` only for an enabled complete line (`main.py:875-918`). Manual `/api/provision` performs reader/PIN/SMSC/IMEI/port checks, saves via `cfg.upsert_instance`, then starts through `_start_engine_checked` (`main.py:4111-4230`). `/api/instances/{iid}/start` validates card identity and PIN and refreshes live reader binding before engine creation (`main.py:5962-6029`). **Do not manually instantiate engines.**
2. **Engine/config:** `config.py:805-885` persists line intent; `render_instance_json`/`write_instance_json` create engine input (`config.py:1192-1343`); `engine.start` checks egress/image/network, renders/replaces per-line Docker container (`engine.py:436-622`). Updating operational line settings via `/api/instances` restarts a running engine and returns `applied`; a pure rename avoids restart (`main.py:5799-5885`). Engine sends callbacks to `/api/engine/event`, authenticated by its own internal token (`gate.py:33-50,129-150`; `main.py:7897`). A second voice proxy would violate this ownership.
3. **eSIM:** MDD already wraps local `lpac` ES9+/ES10b, NDJSON progress and cancellation (`lpa.py:1-10,128+`); default binary is `$MDD_DATA/lpac/lpac` or packaged `/usr/local/bin/lpac` (`config.py:216-230`; `lpa.py:69-95`; `runtime/Dockerfile.control-overlay:2-56`). `/api/esim/chip`, `/profiles`, `/download`, profile enable/disable/delete/nickname and notifications are admin routes (`main.py:8258-8667`). Download accepts `reader[_index]`, optional `se_id`/`aid`, activation code or SM-DP+/matching/confirmation code, then returns `{ok,started,reader,reader_index,se_id,imei}`; progress/error/completed events are emitted on `/ws` (`main.py:8510-8606`). `_esim_guard_engine` refuses exclusive PC/SC access with structured 409 `{code:engine_running,instance_id}` (`main.py:3446-3461`). Modem switch disables/stops impacted lines before touching eUICC and restores prior intent on failure (`main.py:3571-3636,8402-8466`); native-reader branch has a separate fail-closed path. Preserve this state machine and verify rollback for partial failure.
4. **Communications:** SMS `POST /api/instances/{iid}/sms/send` takes `{to,body,transport:auto|vowifi|cellular}` and returns 409 when unavailable (`main.py:7006-7051`). MMS `POST /api/instances/{iid}/mms/send` takes multipart fields `to,text,subject,attachment_ids/attachments,split`, returns stored message(s) immediately, completes asynchronously with `sms` events (`main.py:6646-6709`). Conversations/read marks/unread and MMS part/download routes are at `main.py:6388-6458,6711-6735`; per-line calls and hangup are `main.py:7610-7658`, cellular variants `7687-7731`, softphone provisioning and SIP-over-WebSocket relay `7734-7818`. Calls are not a generic JSON-only audio contract; native call stacks need signalling/media design around the MDD relay.
5. **Carrier, notification, QMI, appearance:** current carrier SIP/CP defaults and override semantics live in `config.py:1068-1170`, carrier identity database in `carrier_id.py:16,157`, and auto-promote merges defaults (`main.py:1070-1144`). Existing outbound dispatcher supports webhook, Telegram, PushPlus, Feishu with independent event/line filters (`config.py:140-221`; `notify_push.py:790-826`), invoked asynchronously from engine event handling (`main.py:8239-8255`); WeCom/Bark/APNs are not found as dedicated dispatchers. Existing host/device cellular state exposes ModemManager registration, operator, signal and data profile (`host/mdd_orchestrator.py:1583-1638`; `main.py:4716-4721,4970-4986`), with QMI reset handling (`runtime/hardware.py:930-970`); a OneWIFI QMI-specific status shape is not present. React WebUI is served by control as hashed static assets (`main.py:8690+`); `webui/src/App.jsx` owns current shell and navigation. OneBoard appearance is therefore an MDD WebUI design change, not a second control backend. Source details of OneWIFI variants require the separately assigned source reconnaissance.

## Recommended shared phone contract (architectural input, not a frozen spec)

- Keep **one HTTPS MDD origin** for iOS and Android. `GET /api/auth/status` currently advertises `api:1`, `features:[client_tokens]` (`main.py:3068-3080`). `POST /api/auth/client/login` takes administrator credentials plus `name,platform,app_version`, returns one-time `{token,client}`; use `Authorization: Bearer <token>` thereafter. `POST /api/auth/client/logout` revokes it (`main.py:3154-3188`; `clients.py:111-155`). `gate.py:27-36,186-214` distinguishes bearer from cookie+CSRF; revocation closes sockets. Do not make native phones imitate browser cookies.
- Discover line IDs through `GET /api/instances`, which intentionally returns only `{id,name,msisdn,enabled,status}` for a client (`main.py:5762-5796`). Use those IDs for `/status`, `/availability`, messages/SMS/MMS/calls/voicemail/softphone paths. `GET /api/instances/{iid}/softphone` supplies ephemeral SIP/media relay details, including `ws_path`, host, username/password and media mode (`main.py:7734-7750`); treat these as sensitive, refresh before calls. `GET /api/messages/unread` supplies badge totals (`main.py:6427-6435`). `/ws` is receive-only for client live `sms,call,voicemail,status,line` events (`main.py:8672-8688`; `authz.py:74-124`). Reconnect, sequence/re-fetch, background push wakeups, and native call signalling still require a contract across iOS/Android; WebSocket alone is not OS background delivery.
- **Security gate:** `authz.py:34-77,80-101` is a fail-closed route/event allowlist. Existing `/api/esim/*`, `/api/devices/*`, `/api/settings` and line start/stop are admin-only. Decide explicitly whether phones need carefully scoped eSIM/admin operations, with user confirmation and separate authorization, or remain communications clients. Do not widen the whole allowlist. Preserve binary/SIM-addressed SMS denial and filtered status (`authz.py:39-45,105-124`; `tests/test_client_signin.py:118-132`).
- **Capability design assessment (INFERENCE/B):** the parent's proposed explicit `manage_devices`, `manage_esim`, `manage_settings` grants are feasible without making every client an admin. `clients.py:61-103,111-155` persists a versioned client record containing a token digest, and `gate.py:60-71,129-150` resolves that record to a principal before `authz.allowed` checks a method/path. Extend the requested capabilities on the password-authenticated `/api/auth/client/login` issuance path, strictly validate a closed vocabulary, persist the *granted* set with the record and carry it into the principal. Missing capabilities on version-1/older records must deserialize to empty, so old tokens retain communication-only access; `platform`/app version/name must not imply privilege. Scope each grant to named route+method+event/data filters in `authz.py`, with `manage_esim` especially guarding destructive profile switch/delete and never granting `/api/engine/event`, account/password, raw SIM OTA, or unrestricted system/update operations incidentally. An already-authenticated client must not self-upgrade grants; any grant change requires a fresh administrator credential/issuance or explicit admin-only revocation/reissue flow. Route-existence, old-token, requested-versus-granted, unauthorized read/write, revoked-socket and event-redaction tests belong in `tests/test_authz.py` and `tests/test_client_signin.py`. Prefer current MDD-native endpoints; add `/api/mobile` only for a genuinely missing adapter backed by MDD ownership, never a legacy voice proxy. Whether a capability permits *all* lines/devices or narrower resources is still an explicit contract decision; current `Principal` has only `client_id` and no per-line assignment (`gate.py:60-71`).
