# MDD mobile contract v1 (implementation target, 2026-10-13)

One MDD HTTPS origin owns all routes and SIM/line lifecycle. `device_id` in page DTOs is an MDD instance ID. An unprovisioned reader is not a callable line. Non-call legacy `/api/X` page routes become `/api/mobile/v1/X`; native auth, `/api/instances/*`, and `/ws` do not get the prefix. There is no legacy fallback.

## Authentication and authorization

- `POST /api/auth/client/login` JSON `{username,password,name,platform,app_version,capabilities:["manage_devices","manage_esim","manage_settings"]}`. `username` is the configured MDD administrator username; password is checked by MDD. Successful **unwrapped** response `{token,client:{id,name,platform,app_version,created_at,last_seen,expires_at,capabilities}}`. Capabilities are requested explicitly, checked against a closed vocabulary and stored per token; omitted capabilities are `[]`. Old tokens/records remain `[]` and cannot self-upgrade.
- `GET /api/auth/status` unwrapped MDD response with `client` public record on bearer authentication for restore. `POST /api/auth/client/logout` revokes bearer and sockets, SIP registrations and owned push endpoints. Clients send `Authorization: Bearer <token>`; browser keeps cookie+CSRF. No client receives administrator privileges.
- Communication routes stay scoped to MDD's current client allowlist. `manage_devices`, `manage_esim`, `manage_settings` each authorize only named route+method sets, including the facade's direct in-process handlers. They never permit internal engine, account/password, system update, raw SIM OTA, or generic admin routes.

## Calls and events

- `GET /api/instances/{iid}/softphone` returns MDD's native unwrapped `{enabled,username,password,ws_path,host,realm,...media}`. Connect WSS at `ws_path` with bearer Authorization and `sip` subprotocol. SIP INVITE/dialog owns dial, answer, hangup, DTMF and media; do not call the legacy JSON PCM endpoints. `GET /api/instances/{iid}/calls` is native unwrapped history. Generic `/ws` supplies MDD events/badges, not call media/signalling.
- Browser and both phone clients register separate contacts on the one line endpoint. The engine forks the currently registered contacts; first answer cancels the other branches. A late-registering native client can answer a still-ringing other branch with a SIP INVITE to `pickup_uri` (`mddpickup-<call_id>`) on the same authenticated per-line UA. Asterisk `Pickup(<call_id>@PICKUPMARK)` finds only the marked, ringing called leg; no global channel pickup. Engine-generated inbound `call_id` is delivered in push data and the `X-MDD-Call-ID` header on each corresponding SIP INVITE, distinct from the history integer, per-fork SIP Call-ID, and OS call UUID. This has static/template proof only, not live fork/pickup proof.
- Outbound engine `call_out` and `call_result out` callbacks carry the caller channel's `${CHANNEL(uniqueid)}` into the same call-history `call_id` column. Exact ID is used for both insert and finalization, including a result that overtakes its start callback. Older engines without an ID retain peer-based compatibility; the updated engine never falls back to a different open call when its ID is supplied. Same-peer reverse-completion is unit-tested, not live engine-tested.

## Page facade

JSON success is `{data: <legacy DTO>}`; errors preserve non-2xx with `{error:{code,message}}`. These are MDD-owned adapters, not HTTP proxying. Required v1 paths, subject to explicit unsupported responses where no real MDD operation exists:

- `GET /api/mobile/v1/dashboard/host`, `/dashboard/devices`, `/devices`, `/devices/{iid}/overview`: MDD host/instance/reader projections. Legacy OneWIFI license `device_limit` is null (distinct from MDD's own `MAX_SIM_LINES=10`), as are `cpu_percent`, `net_rx_bps`, `net_tx_bps` where MDD has no sample; clients must render unavailable, not zero. Reader-only rows use `id=reader:<MDD physical device ID>`, `callable:false`, `reader_id`; `iccid` is projected only from the exact live PC/SC reader name in `hub.cards`. They cannot use `/api/instances/*` until provisioned. Authorized native MDD `GET /api/readers`, `GET /api/sim/detect?reader_index=...`, `POST /api/provision` retain existing reader lock and SIM validation. Cellular registration, IP and interface come only from observed MDD status; unobserved numeric QMI status, dBm, SINR and radio channel remain null/unavailable.
- `PATCH /api/mobile/v1/devices/{iid}/network|vowifi|flight-mode`; `POST .../vowifi/actions/reconnect|actions/reboot`: only operations supported by MDD; never claim state changed before hardware/engine confirmation.
- `GET /api/mobile/v1/sms/contacts`, `/sms/thread?device_id=<iid>&peer=...`, `DELETE /sms/thread`, `POST /sms/send` (`device_id,phone,message`). Send outcome reflects MDD submission, not delivery. `parts_total` and `parts_accepted` are numeric only when supplied by MDD, otherwise null. A definite failure is HTTP 502 with the exceptional retained `{data:{outcome:"failed",parts_total:null,parts_accepted:null,retry_safe:false,...}}` envelope because the iOS sender parses `data` on failure; unavailable/invalid requests use ordinary errors.
- `GET /api/mobile/v1/devices/{iid}/esim`, `/esim/profiles?refresh=1`; `POST .../esim/actions/switch|disable|download`; `PATCH|DELETE .../esim/profiles/{iccid}`. eSIM always resolves iid to an MDD-owned reader and respects locks/identity checks. Switch success returns `{data:{status:"switched"|"already_active",iccid,verified:true,device_id,reader_id}}`; `device_id` is the **post-switch** configured MDD instance only when its ICCID and the live reader association agree, otherwise `reader:<physical ID>` (non-callable), while `reader_id` is the physical MDD ID. Recovery/reader identity disagreement is 503. A client must refresh inventory and relocate to `device_id`; the old iid is not an alias and rejects the different SIM with 409. Download progress is SSE `progress` JSON `{step,msg,pct}` culminating in `done` or `error`. `GET|PUT /api/mobile/v1/cards/{iccid}/policy` is 501 (see below).
- `GET|PUT /api/mobile/v1/settings/preferences|notifications|sms`; `POST .../settings/notifications/{channel}/test`; `GET /api/mobile/v1/system/info`. Preferences persist `language` as `ui_language` (`zh|en`); SMS setting maps `auto_clear_modem_storage` to the actual modem storage policy (`delete|keep`); system `version` comes from MDD `VERSION`, while unknown build time stays empty. `/settings/vowifi` MTU and `/cards/{iccid}/policy` are 501 `unsupported` because MDD has no matching runtime operation. Other source-only settings also return non-2xx, not empty success.
- Paired OTP and device push routes will be specified separately with credential expiry, redaction and per-client ownership. Native mobile call history is `GET /api/instances/{iid}/calls` (unwrapped `{calls:[...]}`); call actions bypass the facade and use SIP. There is no `/api/mobile/v1/devices/{iid}/calls` alias.

The 11 checked-in `contracts/*.json` files are ASGI GET snapshots, not handcrafted examples: host/devices, device overview, SMS contacts, eSIM overview/profiles, preferences, SMS settings, system info, and notification settings. Numeric `timeout_ms` is `5000`; stable test time/host inputs produced matching SHA256 hashes on two successive generations. Treat these fixtures as frozen mobile-client inputs and coordinate any regeneration. Source/unit/build/install/hardware proof is separately reported; missing live reader, cellular/IMS, APNs delivery, SIP fork/pickup, and installed-mobile proof is not implied by a fixture.

## Notification settings and push (implemented source contract)

- WebUI administrator keeps MDD's unwrapped `GET|PUT /api/settings` and `POST /api/notifications/{webhook|telegram|pushplus|feishu}/test`; its existing rich Telegram/webhook/PushPlus/Feishu configuration is retained. Mobile `manage_settings` uses wrapped `GET|PUT /api/mobile/v1/settings/notifications` and `POST /api/mobile/v1/settings/notifications/{telegram|webhook|wecom|bark|pushplus}/test`. The two route families are not aliases. Native mobile `email.enabled=true` returns 501 because there is no mail sender; mobile multi-URL custom webhook returns 501, while WeCom and Bark fan out to 1-10 validated HTTPS URLs independently. Unknown enabled channels do not silently save. `notification-settings.json` is a generated ASGI GET fixture.
- Mobile GET fields are `telegram:{enabled,bot_token,chat_id,admin_id,base_url,proxy}`, `webhook:{enabled,urls,secret,timeout_ms}`, `pushplus:{enabled,token,topic,channel}`, `wecom:{enabled,urls,payload_template}`, `bark:{enabled,urls,group,icon,level}`, `email:{enabled}`, `onetools:{enabled,public_base_url}`. `bot_token`, `token`, `secret`, proxy/base URL, and destination URLs are `********` when set. An unchanged all-mask URL array of identical length retains the entire previous array; mixed masks, inserts and deletes are 409. Replacing destinations requires a complete explicit URL array, and GET never echoes saved destination URLs. A scalar mask retains its saved value. `timeout_ms` is numeric, not a string. MDD-only channel fields such as event filters survive mobile updates. A custom Telegram `base_url` is explicitly unsupported; proxy URL maps to MDD manual proxy mode. Native admin GET continues to expose legacy rich Telegram/webhook/PushPlus/Feishu values; only new WeCom/Bark URLs and APNs key paths are masked there, not every existing secret.
- `GET|POST /api/mobile/v1/settings/notifications/onetools/pairing` returns an expiring `mdd_pair1_` credential in the `onetools://onewifi?u=<origin>&t=<token>` URI and `{v:1,u,t}` QR JSON; POST rotates it. Paired SMS endpoints and `GET /api/mobile/v1/onetools/sms/stream` use that distinct bearer, not the mobile client token. `PUT /api/mobile/v1/onetools/ios/push-endpoint` registers an SMS token with `push_to_start_token:""`, `live_activity_mode:"update_only"`; `PUT .../push-endpoint/live-activity` uses activity-ID/revision compare-and-swap; `POST .../push-endpoint/ack` records SMS receipt. `POST /api/mobile/v1/calls/push-endpoint` uses the MDD client bearer for owned VoIP tokens and revoke cleanup.
- Native admin `GET|PUT /api/settings` accepts separate provider configurations `apns` (SMS and Live Activity update) and `apns_voip` (calls), each with `enabled`, `environment` (`sandbox|production`), `bundle_id`, `team_id`, `key_id`, `auth_key_path`. Enabled saves validate IDs and an existing P-256 `.p8` file. The private key contents are **never** an API field; `auth_key_path` is masked on native GET and an unchanged mask retains it on PUT. `POST /api/notifications/apns/test` is a native administrator action targeting only registered SMS endpoints. Native `POST /api/notifications/wecom/test|bark/test` also exists. Mobile `{channel}/test` supports Telegram/webhook/WeCom/Bark/PushPlus but `apns` remains 501. The admin UI may expose provider setup/test only as controls for these native paths, with no delivery guarantee: mock transport tests prove HTTP/2 request construction and provider acceptance handling, not external APNs acceptance or device delivery. Live Activity uses only an iOS-registered update token; no push-to-start token is accepted. Its activity-ID/revision CAS prevents stale updates and same-ID revival after terminal state; receipt records server-observed acknowledgement only.
