# Acceptance protocol
Source/build checks do not prove runtime. Keep per-step timestamp, installed build IDs, MDD instance ID and redacted reader/card identity; never save bearer token, credentials or raw subscriber IDs in shared report.
1. Verify installed control container/process comes from this MDD build, no NEWONE gateway process/container owns reader; check MDD-created engine labels and one reader lease owner.
2. Login on OneBoard, iOS and Android against exactly that origin. Check MDD token/session registry; both phone session clients identify correct platform and management capabilities. Invalid token/revoked token fails, logout closes SIP.
3. Trigger/read current reader state through MDD. Resolve displayed phone device to the same MDD instance and current card; capture non-sensitive mapping. Provision/start only through MDD control. Observe actual IMS registered, not merely engine running.
4. Place or receive one real call to an explicitly authorized test destination; capture time/direction/instance and resulting MDD call record. Verify bidirectional speech, remote hangup, native ending and history. OneBoard browser earpiece uses MDD JsSIP.
5. Repeat native foreground, background/locked screen, PushKit cold wake (iOS), Android service without Activity. Verify call push -> native UUID -> SIP dialog mapping. Simultaneous browser/iOS/Android registrations: all ring, one answers, other two stop; cancellation before wake and token revocation cannot leave ghost calls.
6. Verify Bluetooth/speaker/mic permissions, interruption, WiFi/cellular transition, direct and TURN-only media paths with actually negotiated compatible codec. Record failure honestly.
7. Send controlled SMS/MMS through MDD and receive reply; verify same-line history and notification/push acknowledgment/Live Activity, no second provider duplicate. Test eSIM only with a recoverable authorized profile and record observed ICCID switch, failed-switch compensation and re-registration; mock tests cannot stand in.
8. Verify carrier effective profile vs explicit override and QMI/module status from MDD actual hardware. Browser and phones agree on same data. Unavailable hardware/provider shows explicit unavailable, not synthetic healthy state.
9. Runtime acceptance can be PASS only when applicable steps have observed evidence. Current host has no known MDD runtime address, reader or connected phone; user must supply environment at final integration step if none becomes discoverable inside allowed roots.
