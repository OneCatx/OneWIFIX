# Backend migration handoff (2026-10-13)

## Implemented source contract

- One MDD origin serves capability-scoped native client login/status/logout, the in-process `/api/mobile/v1` facade, native SIP softphone/history, and pairing-scoped OneTools SMS endpoints. Client tokens do not become browser administrators. Unsupported source-only operations return non-2xx; no second proxy/gateway was added.
- Reader-only inventory remains non-callable and takes its ICCID only from the exact live PC/SC reader. eSIM facade resolves the reader and requires the native operation's observed target ICCID. Native enable includes live-inventory idempotence, locked identity checks and compensation; the facade passes through `already_active` only after native verification. Switch success adds `device_id` and `reader_id` from refreshed reader association: verified new line iid, or a reader-only identity for an unprovisioned profile. Old iid wrong-SIM access remains 409; mismatched recovery association fails rather than returning a false line identity.
- Outbound call callbacks carry exact Asterisk channel unique ID to insert and finalization. Inbound retransmission/early answer are deduplicated in the store. Engine dialplan has multi-contact fork/pickup and call-ID header source coverage, not live SIP proof.
- Mobile notification adapter supports Telegram, custom webhook, PushPlus, WeCom and Bark with masked credentials/URLs and unambiguous whole-array URL replacement. WeCom/Bark destinations dispatch independently for retries. Email, multi-URL custom webhook and unsupported Telegram base URL are rejected. Native admin settings preserve existing rich channels and add validated WeCom/Bark and distinct APNs SMS/VoIP configurations; enabled APNs requires a real local P-256 key. Tests mock transport and never send real notifications.
- Pairing credentials are distinct from client bearer tokens; SMS endpoint registration is update-only for Live Activity. Activity ID/revision CAS rejects stale writes and same-ID terminal revival. SMS ack records a server-side receipt, not APNs/device delivery. VoIP endpoint ownership follows the client and is revoked with it.
- Preferences, modem SMS storage policy and system info use MDD state; unmeasured DTO fields remain unknown. Failed SMS sends retain a 502 `data` outcome for the existing iOS parser. VoWiFi MTU and eSIM card policy have no native runtime equivalent and return 501.

## Second review eSIM transaction follow-up

- Deterministic native-handler RED scheduled enable after its first `_esim_run` returned and paused at post-enable inventory. A same-reader disable completed before enable verification; on resume it would observe the second writer's state and compensate, undoing that independent operation. The test failed with `second writer entered before verification` before repair.
- All same-reader eSIM writers now take `hub.esim_switch_lock(_esim_switch_identity(name)[0])` through their mutation and cache update: enable already held it; disable, delete, nickname, notification process/remove, and the complete background download job now share it. The download request reserves `esim_download_ops` while holding the transaction lock before returning `started`; the job reacquires the same lock, then the reader lock, and releases both reservation and busy flag in `finally` on error/cancellation. `_esim_run` rejects mutations while a reserved download is pending, so a caller that enters between request release and job acquisition cannot perform a competing write. Reader lock remains inner to transaction lock; native enable's inventory, physical-card probe and refresh reacquire it in one block, then release before compensation's own reader-lock acquisition (no nonreentrant lock nesting). Other physical reader keys remain independent.
- Native entry tests prove same-reader disable waits until enable verifies and compensator is not called, while a different reader's disable proceeds; a failing download keeps a same-reader writer waiting and clears busy/operation ownership before it proceeds; cancellation also clears reservation and unlocks. After final edits: `tests.test_esim_profile_switch`, `test_client_signin`, `test_mobile_dto`, `test_onewifi_carrier_profiles`, `test_mobile_call_correlation` **88 tests in 11.375 s, OK**. ## Cancellation intent follow-up

- Active native cancellation now records the exact operation ID's intent before awaiting the process signal, so a signal ignored by lpac, an unsuccessful OS signal, or a normal process exit cannot turn an accepted cancellation into a `completed` event. A post-download card refresh still runs before the terminal event; cancellation during that refresh likewise emits an error with an explicitly unknown outcome. The operation retains its physical reservation until the background job actually exits. A delayed cancellation response neither marks a replacement operation nor broadcasts a stale `cancelling` event.
- The API's `cancelled: true` means **the request was accepted for the matching in-flight operation**, not that lpac terminated or a card mutation was rolled back. LPA's lower-level boolean now means an interrupt signal was sent (or fallback kill succeeded); it is false if both delivery attempts fail. Hardware profile state after interruption may be indeterminate, so the terminal event instructs a profile check before retry. A process that ignores SIGINT can still run until it exits or the existing timeout applies; no new hard-kill guarantee is claimed.
- RED regressions captured a signal-attempt success followed by normal LPAC completion and both OS delivery attempts failing. Green tests additionally cover no active process signal, cancellation during refresh, and old/new operation ownership while signal delivery is delayed. Fresh focused `tests.test_esim_profile_switch` plus `tests.test_client_signin`: **71 tests in 11.825 s, OK**. Parent's 2,073-test broad run predates this fix and is not final evidence.
